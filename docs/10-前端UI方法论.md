# 文档 10：前端 UI 方法论（防止 AI 迭代时界面设计漂移）

## 用途

当项目含前端页面、由 AI 持续迭代，且已经出现过「原本的卡片单选框被后续 AI 改成了下拉选择器」「颜色/间距/组件越改越乱」这类**交互与视觉漂移**问题时，照这份文档搭建前端专项守门。它把「AI 做 UI 时别自作主张重新设计」变成可执行的流程，而不是一句「注意交互统一」。

**核心问题：AI 改前端时，交互/视觉漂移为什么会发生？**

它跟「重复踩坑」（文档 9）不同——这里**每一步都成功，没有报错**，AI 是「顺畅地」把既定交互改掉了还自认为在改进。根因几乎总是：**AI 不知道「卡片单选」是一个既定且必须遵守的事实**。它只看到任务单「做一个选项选择」，于是自由发挥成下拉。所以防漂移 = **把既定事实固化、强制读取、独立把关**。

## 不适用

- 项目没有真实前端页面，或前端不需要设计判断（纯接后端、改文案等无视觉变化）→ 不需要本方法论，会拖慢节奏。
- 单次偶发的样式小问题 → 按文档 3 小改动直接改，不启动整套流程。

## 怎么用

### 双重守门：一个管「生成」，一个管「记忆」

| 守门 | 管什么 | 用什么 | 对应参考 |
|---|---|---|---|
| **生成侧** | 这次做界面时别漂移设计方向、别随手自定义组件 | 成熟的 UI design skill（如 [oil-ui](https://github.com/oil-oil/oil-ui)）所封装的流程 | 本份文档「怎么用」第 1 节 |
| **记忆侧** | 让每个新 AI 会话都知道既有事实、强制复用、审查时抓漂移 | `DESIGN.md` 规范文档 + 强制阅读 + 审查检查项 | 文档 11 的 DESIGN.md 模板 |

**两者互补**：UI skill 守「怎么做界面的过程」，`DESIGN.md` 守「既有事实的记忆与验收」。缺了任一，漂移都挡不住。

### 1. 生成侧：让 AI 走「先认品类、后动手」的流程

吸收 oil-ui 的关键机制，写进前端任务约定：

- **小改动边界**。任务必须分级：用户已点名改哪个元素、怎么改 → 直接改，不盘点、不重设计；「改造流程 / 加新功能 / 优化 UI」→ **沿用现有视觉，不走视觉方向探索**。这条直接挡住「后续 AI 想动既有交互」。
- **产品事实先行**。开工前先写清用户、品牌、任务、设备、**已有交互基线**；「必须保留的交互基线」是黑名单，改动要先说清理由。卡片单选既然是基线，就不能默认换成下拉。
- **既有项目先复用**。明确原则：存量项目先复用有效的设计变量、组件和交互习惯，修问题从源头修，**不为一次调整另造设计系统**，也不把无关代码重构混入视觉工作。
- **独立评审**。有主要操作流程时，派一个无历史上下文的全新评审者（能看图），只看当前画面、任务和约束，不看制作过程和代码。作者不审自己（呼应文档 0 常驻规则 #4）。
- **撞脸与默认惩罚**。「高级、精致、简洁」这类模糊词必须翻译成可观察的决定，禁止直接当设计理由；不许贴着某标杆换皮。

### 2. 记忆侧：落地 `DESIGN.md` 规范文档

把项目散落的颜色、间距、通用组件、交互基线，统一固化进一份 `DESIGN.md`（模板见文档 11），并配三道强制：

1. **事实要落地**：已确定的交互（卡片单选是我们决定的）、色彩 token、间距、通用组件，写入 `DESIGN.md`；不是留在聊天里。
2. **事实要强制读**：每个前端任务会话开始前，强制先读 `DESIGN.md`，并作为 `acceptance_criteria` 的白名单。做法：在 `AGENTS.md`（文档 1）的强制阅读顺序里加入 `DESIGN.md`；在前端任务单里让 AI 引用它涉及的设计 token / 组件。
3. **事实要机器验**：审查/验收时，专门检查「交互与视觉是否与 `DESIGN.md` 一致」——卡片是否还是卡片单选、颜色是否复用 token、组件是否复用现有组件。在文档 7 的审查清单里加一条交互一致性检查项。

### 3. 未实现可自动拦截的部分用「人工/审查把关」

交互与视觉是否「长得像」既定设计，**无法用正则 lint 拦截**（lint 只能查代码结构，看不出界面长得像不像卡片）。所以这套必须靠「开工前读事实 + Review 抓漂移」这类人工/审查把关——这正是文档 0「作者不审自己」的用武之地。

## 常见错误 / 注意事项

- **别把 lint 神话**：lint 能拦「硬编码颜色、重复组件」这类代码结构问题，但拦不住「视觉长相漂移」。二者都要，别只上一个。
- **每条既定交互都要有出处**：`DESIGN.md` 里每条「卡片用单选」都要写清为什么这么定，否则下一个 AI 又会凭「通用常识」质疑它。
- **`DESIGN.md` 要定期清理**：它应该跟着项目长，但过期的条目要删（呼应文档 4 的文档过期治理），否则会变成没人看的长文。
- **UI skill 只负责设计判断**：不拿它写业务逻辑、接后端；前端实现仍按项目自己的约定。
