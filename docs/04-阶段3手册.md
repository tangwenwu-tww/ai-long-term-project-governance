# 文档 4：阶段 3 手册（持续迭代 1→99）

**进入条件**：阶段 2 验收通过，且至少一个升级触发信号出现。

## 步骤

### 1. 上四角色 + 状态机

| 角色 | 职责 | 硬约束 |
|---|---|---|
| PM / Orchestrator | 读文档、拆任务、派任务、收证据 | 只调度，不改代码 |
| Planner | 输出结构化计划 | 计划须经独立 Review 才进入执行 |
| Executor | 基于任务单实现 | 先写测试（red），再实现（green），附证据 |
| Reviewer | 独立上下文审查 | 作者不能审自己；必须含 pre-mortem |

**状态集**：

```
PLANNED → EXECUTING → REVIEW_PENDING → VERIFIED → CLOSED
                ↑            │
                └── REVIEW_REJECT
任意状态 → RETRY_EXHAUSTED / STALL_DETECTED → HALTED_FOR_HUMAN
```

**跃迁条件**：

| 当前 | 事件 | 条件 | 目标 |
|---|---|---|---|
| PLANNED | START_EXECUTION | 任务单含 acceptance_criteria、allowed_files、pre_implementation_search | EXECUTING |
| EXECUTING | SUBMIT_FOR_REVIEW | 证据包格式合法且非空 | REVIEW_PENDING |
| REVIEW_PENDING | REVIEW_PASS | decision: PASS 且无 Critical | VERIFIED |
| REVIEW_PENDING | REVIEW_REJECT | decision: REJECT 且含至少一条可操作项 | EXECUTING |
| VERIFIED | MERGE | CI gate 全过，diff 只在 allowed_files 内 | CLOSED |
| 任意 | RETRY_EXHAUSTED | 同一 failure signature 连续 ≥ 3 次 | HALTED_FOR_HUMAN |
| 任意 | STALL_DETECTED | 连续 3 轮修改文件集相同且 diff 变化 < 10% | HALTED_FOR_HUMAN |

“连续失败”按**不同 failure signature** 计数，成功一次即清零。

### 2. 跃迁由证据校验驱动

证据包必须为结构化 JSON（模板见文档 8）。硬规则：
- `exit_code` 必须显式记录为 0；
- 只写“测试通过”而无命令和退出码 → 格式不合规，拒绝跃迁；
- `stdout_sha256` 用于防事后改写；
- Reviewer 在独立上下文**重新运行核心命令**，用自己的退出码与证据比对，不一致即证据不可信。

### 3. 测试三层金字塔 + 路由

- 单元 ≈ 70%：纯逻辑，无网络、无 DOM。
- 集成 ≈ 20%：模块接缝，验证数据流和接口契约。
- E2E ≈ 10%：真实用户路径，合并前或定时运行。

路由规则写入 CI：只改 `module-a` → 只跑 `module-a` 的单元+集成；跨模块变更才升级到 E2E。

> **补充（出处：文档 12）**：若「AI 反复跑全量/重型测试浪费时间」成为痛点，按 [文档 12：测试分层](./12-测试分层.md) 把重型测试从日常剥离、清理机械表面单测、聚焦基础可用性 + 历史 Bug 回归两类高价值测试——不追求金字塔比例，而是按耗时分轻重。

### 4. 测试债扫描

识别模式：`NO_ASSERTION`、`ONLY_MOCK_ASSERTIONS`、`HOLLOW_ASSERTION`、`ASSERT_TRUE`、`HEAVY_MOCK_LOW_ASSERT`、`UNCONDITIONAL_SKIP`。
- 新增测试命中任一 → 阻断合并；
- 存量用 baseline 容忍，开启 `--fail-on-new`；
- 重点模块可跑聚焦变异测试，范围限定当前模块。

### 5. 技术债硬性排期（70/20/10）

每个迭代（2 周）固定按比例分配工作量，防止「只堆新功能、债务野性生长」：

| 占比 | 用途 |
|---|---|
| 70% | 新功能开发 |
| 20% | Bug 修复 |
| 10% | 技术债偿还（清理冗余代码、更新过期文档、重构重复逻辑） |

**动态调整信号**：若发现 AI 开始频繁重复造轮子、或同一功能被用不同方式实现两次以上，说明技术债已拖累开发效率，把偿还比例提到 20–30%（对应压缩新功能额度），直到重复造轮子的现象回落。此比例为排期约束，非建议。

### 6. 文档全生命周期治理

状态：`DRAFT / REVIEW / ACTIVE / NEEDS UPDATE / DEPRECATED / ARCHIVED`。

**过期触发条件（任一）**：6 个月无更新；引用功能/API 已废弃；示例无法运行；链接 404；无明确 owner。

**处置**：优先归档而非硬删；`ARCHIVED` 必须附 `archived_date`、`reason`、`replacement_link`；硬删前归档区保留 ≥ 90 天；ADRs 永不自动归档。

**AI 读取规则**：`NEEDS UPDATE / DEPRECATED / ARCHIVED` 不得作为实现依据，引用前必须检查 frontmatter 的 `status`。

> **执行指令见[文档 13：文档巡检](./13-文档巡检.md)**：它给出可交给 AI 的巡检提示词，含「怎么判、怎么改、怎么归档、怎么精简」，并以本节的归档规则为护栏（删 → 归档、ADR 永不自动归档）。

### 7. PoC 升级为评分卡

- 成功标准在构建前固定：数值阈值 + 测量方法 + 判定人；
- 测试集在原型前准备：约 60% 常规、25% 困难、15% 边界，部分保留不调参；
- 0–5 分制，置信度分级：高（硬门槛全过且 ≥80% 维度 ≥4）、中（主要维度集中 3 分）、低（任一硬门槛失败或主要维度 ≤2）；
- **低置信度不进入选型**，硬门槛失败立即终止。

### 8. 完整 Worktree 并行

3–5 个，每个绑定独立 AI 会话；共享 `.git`；集成优先 `rebase`；定期 `git worktree prune`；每个 Worktree 独立数据隔离。

**产出物**：状态机与证据门控、测试金字塔与路由、测试债扫描、技术债 70/20/10 排期、文档状态机、评分卡、Worktree 卫生规则。

**验收**：任意变更可追溯到任务单、证据包、审查记录；新债务无法进入主干；过期文档不会被 AI 当作依据。

**升级触发**：出现必须长期承担 SLA/合规责任的模块 → 阶段 4。
