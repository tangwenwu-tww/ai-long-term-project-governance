# 文档 6：文档写作规范

## 核心准则（写入 `AGENTS.md` 的原文）

> **每份文档的第一读者是“三个月后已经忘了上下文的你”。文档必须让读者在 30 秒内回答三个问题：这是什么、我什么时候该看它、照着它怎么做。答不出任一问题，文档不合格。禁止只复述代码签名、参数表或实现过程而不给具体用法。**

三条禁令：
1. 禁止无用途文档：开头没有“解决什么问题、谁在什么场景下读”的，不合格。
2. 禁止复述型文档：只抄签名/参数、不解释“为什么用、什么时候用、怎么用”的，不合格。
3. 禁止 AI 自判可读性：由人工做 5 秒测试判定，AI 不能自称“已清晰”。

## 文档类型只能四种

| 类型 | 回答的问题 | 必须包含 |
|---|---|---|
| how-to（README/用法） | 怎么用 | 一句话用途、最小可运行示例、常见错误 |
| adr（决策记录） | 为什么这么选 | 背景、选项、决定、推翻条件 |
| runbook（操作手册） | 出事了怎么做 | 触发条件、步骤、验证、回滚 |
| reference（接口参考） | 签名和参数是什么 | 签名、参数、**每项配一个示例** |

“设计方案”“架构说明”这类 AI 最爱写的，**要么归入 ADR，要么不写**。

## 强制结构模板

```markdown
---
type: how-to | adr | runbook | reference
purpose: 一句话说明这份文档解决什么问题
audience: 谁在什么场景下读
status: draft | active
---

## 用途
（1–2 句，说清什么时候该看）

## 不适用
（什么情况下不要看这份，去看哪份）

## 怎么用
（最小可运行示例，可直接复制；不是伪代码）

## 常见错误 / 注意事项
（踩过的坑，每条一句）

## 更新记录
（日期 + 改了什么）
```

硬规则：**缺 `purpose` 或 `audience` → Reviewer 直接打回。**

## 三个可执行测试

- **5 秒测试（人工）**：5 秒内说不出“干嘛的、什么时候用”→ 重写开头，不是补内容。
- **三问测试（Reviewer）**：谁在什么时候看？照着能不能完成一件事？有没有可复制运行的示例？任一答不出 → `decision: REJECT`，理由写“文档不可执行”。
- **复述检测（脚本辅助）**：某节只有签名/参数表/函数列表，且无“什么时候用、为什么用、示例调用”→ 标记 `RESTATEMENT_ONLY`，不合格。reference 类允许列签名，但每项必须配示例。

## 反例 / 正例

**反例（不合格）**：
```markdown
## useAuth
useAuth 是一个用于认证的 hook，返回认证状态和用户信息。
参数：options - 配置对象
返回值：包含 user、loading、error 的对象
```

**正例（合格）**：
```markdown
## useAuth —— 在组件里读取当前登录用户

**什么时候用**：组件需要知道“谁登录了”或“是否登录”时。
**不要用**：服务端或 API 层判断权限，那里用 getSession()。

**最小示例**：
const { user, loading } = useAuth();
if (loading) return <Spinner />;
if (!user) return <LoginButton />;
return <span>{user.name}</span>;

**注意**：挂载时发起一次 /me 请求；同页多次调用会去重。
```

区别不在写得多，而在正例回答了“什么时候用、怎么用、有什么坑”。

## 落地位置

1. **任务单加字段**：任何“写文档”任务必须写明 `doc_type`（四选一）和 `doc_purpose`。缺字段视为任务未完成。
2. **审查清单加一条 Critical**：`DOC_NOT_EXECUTABLE`——缺 purpose/audience、无最小示例、命中 `RESTATEMENT_ONLY`，阻断合并。
3. **清理权**：改不到可读的文档**直接删掉**，不要留着。看不懂的文档比没有文档更有害。
