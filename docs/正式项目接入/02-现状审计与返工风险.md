# 现状审计与返工风险

## 背景

本仓库已经证明：全新 Executor 只读取目标项目本地治理实例，可以识别阶段、遵守任务范围、生成可复核证据，并接受独立 Reviewer；门禁也能执行阶段晋升和失败止损。

这证明的是**协议闭环可行**，不是“当前 PoC 目录就是正式产品架构”。如果现在直接围绕 `poc/minimal-target/` 开发安装器，会把实验期间的偶然选择固化为长期兼容承诺。

## 审计依据

```powershell
python -m unittest discover -s poc/tests -v
python poc/minimal-target/.ai-governance/gate.py audit --project poc/minimal-target --task tasks/T-AGENT-001.json --evidence evidence/T-AGENT-001.json --review reviews/T-AGENT-001.json
python poc/minimal-target/.ai-governance/gate.py audit --project poc/minimal-target --task tasks/T-GOVERNANCE-002.json --evidence evidence/T-GOVERNANCE-002.json --review reviews/T-GOVERNANCE-002-R2.json
Test-Path -LiteralPath .git
```

已知事实：17 项 PoC 测试及两项实际 Agent 审计通过；仓库当前没有 `.git`，因此尚不能验证 `changed_files` 与真实 Git diff 一致。

2026-11-24 的[首次独立审查](./审查/2026-11-24-02-03独立审查.md)重新运行 17 项测试和两项 audit，退出码均为 0；`Test-Path .git` 的关键输出为 `false`，不是仅凭退出码推断。审查时本文 SHA-256 为 `a5caa269a70355d65ccb21bac9aef3722852d4d1263faa62838b75020ef06a92`，Reviewer 对本文单独结论为 PASS。后续文本如发生变化，必须重新计算哈希并复审。

## 总体判断

| 判断 | 结论 |
|---|---|
| 方法论方向 | 合理，阶段化治理比“一次上满所有规则”更适合长期 Agent 项目 |
| 本地治理实例 | 合理，是实现跨会话稳定性的必要边界 |
| 任务、证据、独立审查协议 | 值得保留，已经有行为证据 |
| 当前 Python gate | 只适合 PoC；不应直接成为正式公共 API |
| `minimal-target` 目录 | 是测试夹具，不是安装模板 |
| 当前信任机制 | 证明“信任锚可行”，但尚未形成可部署的安全边界 |
| 当前成熟度信号 | 可表达阶段规则，但数据仍靠声明，不能直接作为自动晋升依据 |

## 资产处置建议

### 保留为长期不变量

1. **目标仓库本地自包含**：新 Agent 不依赖方法论源仓库的实时可用性。
2. **阶段化门禁**：后续阶段只能增加约束，不得静默减少已有门禁。
3. **任务契约**：验收标准、允许文件、实现前检索缺一不可。
4. **可重算证据**：命令、退出码、stdout 产物与哈希必须能由 Reviewer 重算。
5. **独立审查**：阶段 2 起作者与 Reviewer 不能是同一 Agent 会话。
6. **失败止损**：同签名三次失败和阶段 4 总失败上限必须由机器执行。
7. **生命周期判断**：未到创建时机的文件不能被误判为遗漏。

这些是不依赖 Python、Node、CLI 或插件形态的产品契约。

### 必须在产品化前重构

| 当前做法 | 为什么代价会变高 | 产品化前要求 |
|---|---|---|
| `gate.py` 只存在于 PoC 目标目录 | 上游没有唯一实现源；复制到多个项目后会漂移 | 建立 canonical runtime 源和版本清单，再生成或 vendoring 到目标项目 |
| JSON 结构由代码隐式解释 | 字段变更会造成静默不兼容 | 为 manifest、task、evidence、review、state、approval 建正式 schema 与版本 |
| `changed_files` 由 Agent 自报 | Agent 可漏报或误报 | 与 Git diff/暂存区做机器比对；无 Git 时明确降级或拒绝高阶段审计 |
| Agent/session 身份由 JSON 字符串声明 | 任意 Agent 可以伪造身份 | 从编排器或受信执行环境注入身份，证据只引用不可自填的运行 ID |
| `trust.json` 与执行代码同仓库同权限 | 有写权限的 Agent 可同时改规则与信任锚 | 信任锚由 CI、操作系统权限或外部签名体系保护；普通任务不得修改 |
| maturity 指标手工填写 | Agent 可通过改数字触发升级 | 区分可自动采集指标、人工事实与审批；机器只提出升级建议 |
| Python 是默认运行时 | 目标仓库未必有 Python；Windows 中文路径已经暴露入口问题 | 通过选型验证目标环境覆盖、分发方式和可移植性后再定技术栈 |
| stdout 文件永久累积 | 长项目会产生大量低价值证据文件 | 定义保留期、压缩、索引、敏感信息清理和审计归档策略 |

### 禁止直接进入正式模板

- PoC 中固定的项目名、Agent ID、session ID 和 task ID。
- PoC `trust.json` 中的示例哈希。
- `phase: 3` 的默认值。
- `poc/minimal-target/` 整目录复制。
- 依赖当前工作目录和具体 Python 命令拼接的调用方式。
- 把 `reviews/*.json` 中的声明身份当作真实信任来源。

## 高返工风险排序

### P0：先解决，否则不要写安装器

1. **实例契约未冻结**：不知道哪些文件由工具拥有、哪些由项目拥有，升级时必然覆盖用户事实。
2. **信任边界未定义**：Agent、人工、CI 都能改同一文件时，“人工批准”和“独立审查”只是声明。
3. **没有 schema/version**：一旦安装到多个项目，任何字段调整都会成为迁移问题。
4. **没有 canonical source**：PoC 目标目录同时承担示例、实现和测试基线，职责混乱。

### P1：正式实现第一版前解决

1. 仓库未纳入 Git，无法实现真实 diff 校验和可恢复更新。
2. 审计时交付运行时尚未选型；该风险的“语言/载体未决”部分现已由 [DEC-2026-11-24-001](../decisions.md) 选择 Go 后关闭，可信签名和目标环境发布覆盖仍待正式验证。
3. 完整任务状态机尚未实现，现有状态仅覆盖失败和阶段晋升。
4. 上游更新与项目本地修改如何三方合并尚无规则。

### P2：试点接入前解决

1. 证据归档与敏感信息清理。
2. 多平台路径、编码、换行与 shell 差异。
3. 遥测、诊断和故障恢复体验。

## 审计建议及后续状态

审计时建议：**保留协议和测试意图，冻结 PoC 扩建；先定义治理实例规范，再做带来源的交付方式选型。**

该顺序已经执行：治理实例规范完成冻结，Go/Node 完成三平台与安装生命周期对比，项目负责人最终选择 Go。权威架构决定见 [`docs/decisions.md`](../decisions.md)；本审计仍用于约束“不要直接产品化 PoC”。

## 推翻条件

若能证明现有 PoC 目录已经具备以下全部证据，可取消“先重构再产品化”的建议：

- 有唯一 canonical source；
- 有稳定 schema 与迁移策略；
- 有受保护的身份和信任来源；
- 能在至少两个不同技术栈项目安全、幂等地安装与升级；
- 实际 Git diff 与证据可自动一致性校验。

当前没有这些证据。
