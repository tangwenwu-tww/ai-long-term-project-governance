## 正式分发模型建议

### 决定

v0 采用以下唯一正式模型：

1. **构建载体**：Go 原生可执行文件；正式构建工具链固定为 Go `1.27.4`，升级工具链必须形成新任务和回归证据。
2. **权威分发渠道**：GitHub Releases。每个版本使用不可复用的 SemVer tag；已发布资产不得原位替换，修复必须发布新版本。
3. **v0 支持平台**：Windows amd64、Linux amd64（glibc runner 边界）和 macOS arm64。未经过同口径原生测试的平台不进入支持声明。
4. **发布资产**：三个压缩后的平台二进制、`SHA256SUMS`、机器可读 release manifest、变更说明和 GitHub artifact provenance attestation。
5. **可信发布门槛**：Windows 稳定资产必须通过 Authenticode；macOS 稳定资产必须通过 Developer ID 签名与 notarization；GitHub provenance 和 SHA-256 不能替代操作系统签名。凭证未就绪时只允许标记为 pre-release/unsigned，不得称为可信稳定发布。
6. **安装方式**：v0 不使用 `curl | shell`、自更新器或系统级包管理器作为主入口。用户或受控 Agent 下载明确版本，先验证 manifest、摘要与 provenance，再运行 `plan`。
7. **目标项目运行方式**：安装器把版本化 runtime/schema 与哈希清单写入目标仓库；日常 Agent 只依赖目标仓库，不依赖 GitHub、全局 CLI 或本方法论仓库在线。
8. **升级与回滚**：升级必须显式执行 `upgrade-plan`，经批准后 `upgrade-apply`；只更新工具管理文件，不覆盖项目事实；失败恢复写入前快照，最近一次成功升级可精确 rollback。

### 为什么选择 GitHub Releases

| 候选 | 结论 | 原因 |
|---|---|---|
| GitHub Releases | 采用 | 当前跨平台实验已经运行在 GitHub Actions；Release 能把 tag、说明和二进制资产放在同一版本边界，且可用 Actions 生成 provenance |
| 把二进制提交到方法论仓库或每个目标项目 | 排除 | 扩大仓库体积和安全补丁传播成本；Node SEA 对比实验已经量化该风险，Go 也不应把发布产物当源码 |
| winget/Homebrew/apt 作为 v0 主渠道 | 暂缓 | 三套包元数据、审核与升级语义会提前扩大维护面；稳定 Release 验证后可作为镜像入口，但不能成为唯一来源 |
| CLI 自更新或独立下载服务 | 排除 v0 | 增加远程信任、并发替换和失败恢复面；与“显式 plan、可审核升级”原则冲突 |

官方证据：

- [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)：Release 可把软件、说明和二进制文件按版本交付。
- [GitHub artifact attestations](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds)：attestation 用于证明产物在何处、以何种方式构建。
- [Microsoft SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool)：Windows 文件签名与时间戳的官方工具边界。
- [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)：macOS 分发前通过 notarization 增强用户对软件的信任。

### 已接受风险与推翻条件

- GitHub 不可用时，新安装和取新版本受阻，但已经实例化的目标项目必须继续离线运行。
- Windows/macOS 稳定发布在取得真实签名凭证前保持阻断；不得用自签名证书降低门槛。
- 若 GitHub Releases 无法满足组织合规、区域可用性或来源证明要求，应增加受控镜像；镜像必须保持同一 manifest、摘要和 provenance，不能产生第二套版本事实。
- 若包管理器成为主要用户入口，可新增 winget/Homebrew/apt，但 GitHub Release 继续作为 canonical artifact source，除非新 ADR 明确推翻。
