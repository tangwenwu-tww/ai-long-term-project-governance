## 正式分发模型建议

### 决定

v0 采用以下唯一正式模型：

1. **构建载体**：Go 原生可执行文件；正式构建工具链固定为 Go `1.27.4`，升级工具链必须形成新任务和回归证据。
2. **权威分发渠道**：GitHub Releases。每个版本使用不可复用的 SemVer tag；已发布资产不得原位替换，修复必须发布新版本。
3. **v0 支持平台**：Windows amd64、Linux amd64（glibc runner 边界）和 macOS arm64。未经过同口径原生测试的平台不进入支持声明。
4. **发布资产**：Windows 为包含已签名 `.exe` 的 `.zip`，Linux 为 `.tar.gz`，macOS 为包含已签名二进制且可 stapling 的 `.dmg`；同时发布 `SHA256SUMS`、机器可读 release manifest、变更说明和每个资产的 provenance attestation。
5. **Provenance 资格门槛**：公开仓库可使用 GitHub artifact attestations；私有/内部仓库只有在已验证 GitHub Enterprise Cloud entitlement 时才允许把它作为稳定发布门禁。若当前仓库不满足，必须先由人工批准专用公开发布仓库，或启用并验证 Enterprise Cloud；两者都没有时只允许 pre-release，不得静默省略 provenance。
6. **可信发布门槛**：Windows 稳定资产必须通过 SHA-256 Authenticode、RFC 3161 可信时间戳和预期发布者身份验证；macOS 稳定资产必须通过 Developer ID 签名、hardened runtime、notarization、ticket stapling 与 Gatekeeper 验证。GitHub provenance 和 SHA-256 不能替代操作系统签名。凭证未就绪时只允许标记为 pre-release/unsigned，不得称为可信稳定发布。
7. **安装方式**：v0 不使用 `curl | shell`、自更新器或系统级包管理器作为主入口。用户或受控 Agent 下载明确版本，先验证 manifest、摘要、provenance 与平台签名，再运行 `plan`。
8. **目标项目运行方式**：安装器把版本化 runtime/schema 与哈希清单写入目标仓库；日常 Agent 只依赖目标仓库，不依赖 GitHub、全局 CLI 或本方法论仓库在线。
9. **升级与回滚**：升级必须显式执行 `upgrade-plan`，经批准后 `upgrade-apply`；只更新工具管理文件，不覆盖项目事实；失败恢复写入前快照，最近一次成功升级可精确 rollback。

### 为什么选择 GitHub Releases

| 候选 | 结论 | 原因 |
|---|---|---|
| GitHub Releases | 采用 | 当前跨平台实验已经运行在 GitHub Actions；Release 能把 tag、说明和二进制资产放在同一版本边界，且可用 Actions 生成 provenance |
| 把二进制提交到方法论仓库或每个目标项目 | 排除 | 扩大仓库体积和安全补丁传播成本；Node SEA 对比实验已经量化该风险，Go 也不应把发布产物当源码 |
| winget/Homebrew/apt 作为 v0 主渠道 | 暂缓 | 三套包元数据、审核与升级语义会提前扩大维护面；稳定 Release 验证后可作为镜像入口，但不能成为唯一来源 |
| CLI 自更新或独立下载服务 | 排除 v0 | 增加远程信任、并发替换和失败恢复面；与“显式 plan、可审核升级”原则冲突 |

官方证据：

- [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)：Release 可把软件、说明和二进制文件按版本交付。
- [GitHub artifact attestations](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds)：attestation 用于证明产物在何处、以何种方式构建。
- [Microsoft SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool)：Windows 文件签名与时间戳的官方工具边界。
- [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)：macOS 分发前通过 notarization 增强用户对软件的信任。

### 可信稳定发布的可执行验收

release manifest 必须把 tag、commit、Go 工具链版本、目标平台、资产文件名、字节数、SHA-256、签名状态和 attestation identity 绑定在同一份记录中。以下任一门禁失败，Release 只能保持 draft/pre-release，不能标记 stable。

**GitHub provenance**：

1. 发布任务先记录仓库 visibility 与 plan/entitlement；私有或内部仓库必须证明 GitHub Enterprise Cloud 可用。
2. 每个 `.zip`、`.tar.gz`、`.dmg` 和 release manifest 都生成 attestation。
3. 在独立下载目录执行 `gh attestation verify <asset> --repo <owner/repo>`，验证 identity、digest、workflow 与 release manifest 一致。
4. 不满足 entitlement 时只能走“人工批准专用公开发布仓库”或“启用 Enterprise Cloud”两条路径；不得以单独 SHA-256 冒充 provenance。

**Windows amd64**：

```powershell
signtool sign /fd SHA256 /tr <trusted-rfc3161-url> /td SHA256 /n <expected-publisher> aigov.exe
signtool verify /pa /all /v aigov.exe
```

验证必须同时确认：文件摘要算法为 SHA-256、证书链受信、publisher subject/thumbprint 与发布策略一致、RFC 3161 时间戳存在且时间戳链有效。签名私钥和时间戳凭证不得写入仓库或交给任务 Agent。

**macOS arm64**：

```bash
codesign --force --options runtime --timestamp --sign "Developer ID Application: <expected-team>" aigov
codesign --verify --strict --verbose=2 aigov
codesign --force --timestamp --sign "Developer ID Application: <expected-team>" aigov-darwin-arm64.dmg
codesign --verify --strict --verbose=2 aigov-darwin-arm64.dmg
xcrun notarytool submit aigov-darwin-arm64.dmg --wait --keychain-profile <profile>
xcrun stapler staple aigov-darwin-arm64.dmg
xcrun stapler validate aigov-darwin-arm64.dmg
spctl --assess --type open --context context:primary-signature --verbose=4 aigov-darwin-arm64.dmg
spctl --assess --type execute --verbose=4 <mounted-dmg>/aigov
```

DMG 内只能包含经过 Developer ID 签名并启用 hardened runtime 的最终二进制；notary 结果必须为 accepted，ticket 必须成功 staple 并在独立机器/干净环境通过 Gatekeeper。Apple 凭证与 keychain profile 只存在于受信发布环境。

### 已接受风险与推翻条件

- GitHub 不可用时，新安装和取新版本受阻，但已经实例化的目标项目必须继续离线运行。
- Windows/macOS 稳定发布在取得真实签名凭证前保持阻断；不得用自签名证书降低门槛。
- 发布仓库 visibility/plan 未定不会被掩盖为“以后再说”：在专用公开发布仓库与 Enterprise Cloud 两条路径都未获批准前，稳定发布保持阻断。
- 若 GitHub Releases 无法满足组织合规、区域可用性或来源证明要求，应增加受控镜像；镜像必须保持同一 manifest、摘要和 provenance，不能产生第二套版本事实。
- 若包管理器成为主要用户入口，可新增 winget/Homebrew/apt，但 GitHub Release 继续作为 canonical artifact source，除非新 ADR 明确推翻。
