# T-EVIDENCE-001 R1：阶段 1 机器可复核证据契约

## 用途

修复 `T-E2E-001 e2e-001-a001` 暴露的 `NOT_VERIFIABLE`：不再依赖 Executor 在最终回复中手工转录命令、退出码和变更文件，而由工具在任务前封存基线、任务后直接运行验证命令并生成可独立重算的 evidence manifest。

本任务只冻结输入、CLI、输出和红灯测试边界；项目负责人批准前不添加测试，批准后也不在本任务实现生产代码。`T-HALT-001`、三平台 CI 和 `e2e-001-a002` 继续保持独立后续任务。

## 当前事实

- `aigov` 当前只有 `plan` 和 `apply`，没有 evidence schema、基线快照、命令捕获或 `submit-evidence`。
- `instance.json.resources.evidence_store` 已声明默认路径 `governance/evidence`，但当前 apply 不创建该目录或 runtime。
- `e2e-001-a001` 的最终回复有退出码和 `changed_files`，但两个验证项缺少完整可重放命令，保护性扫描也无法证明内容未变，因此独立 Agent 只能判定 `NOT_VERIFIABLE`。
- 真实目标可以是无 Git 的 plain directory，因此 `git diff --name-only` 不能成为通用 `changed_files` 事实源。

## R1 候选契约

### 1. 两段式捕获

新增两个实验命令，均需显式 feature flag：

```text
aigov evidence begin   --project <root> --request <request.json>
aigov evidence collect --project <root> --request <request.json> --begin-sha256 <64hex>
```

- `begin` 必须在 Executor 修改前运行；它验证 request，遍历项目树，并在 `evidence_store/<task_id>/<attempt_id>/` 原子创建 `request.json` 和 `baseline.json`。stdout 是写有 request SHA-256、baseline SHA-256 与排除规则的单行 canonical JSON receipt。
- `collect` 必须提交完整 `begin` stdout 的 SHA-256；工具重算 request 与 baseline，不一致即零执行、零覆盖。
- `collect` 按 request 顺序直接启动每个 executable 及 argv，不经 shell 重新解析；所有命令完成后再扫描 post-state，因此验证命令自身产生的变更也不会被隐藏。
- 任一命令的实际退出码不等于 `expected_exit_code`、验收映射未通过或越界时，`collect` 仍封存事实 manifest，但自身返回 1；契约/输入/安全错误返回 2 且不运行用户命令。
- 实验期必须显式设置 `AIGOV_ENABLE_EXPERIMENTAL_EVIDENCE=1`；未设置时返回 2，不创建 attempt 目录、不执行 request 命令。

### 2. evidence request 0.1-draft

request 是受控编排器或项目负责人在任务开始前冻结的 JSON，至少包含：

```json
{
  "schema_version": "0.1-draft",
  "task_id": "T-EXAMPLE-001",
  "task_revision": 1,
  "attempt_id": "a001",
  "task_sha256": "<64hex>",
  "allowed_files": ["src/", "tests/*.json"],
  "acceptance_criteria": [
    {"id": "AC-01", "text": "core verification passes", "command_ids": ["verify-core"]}
  ],
  "commands": [
    {
      "id": "verify-core",
      "executable": "go",
      "args": ["test", "-count=1", "./..."],
      "cwd": "tool",
      "expected_exit_code": 0
    }
  ]
}
```

规则：

- ID、revision、attempt 和 `task_sha256` 全部必填；它们绑定任务文本而不依赖 Agent 的口头转述。
- `executable` 与 `args` 保留完整 argv；`cwd` 是相对 project root 的 slash-normalized 路径。v0 不接受 shell command string、管道、重定向或用户提供的环境变量覆盖。
- 所有 acceptance criterion 必须至少引用一个 command ID；机器仅根据实际退出码计算 `verified`，不接受 Agent 填写的布尔结论。
- `allowed_files` 只允许项目相对普通路径、以 `/` 结尾的递归目录前缀，或单路径段内的 `*`/`?` 模式；拒绝绝对路径、`..`、反斜杠和 `**`。

### 3. baseline 与 changed_files

- 从 project root 递归记录普通文件的 slash-normalized path、byte length 和内容 SHA-256；symlink 记录链接文本但绝不 follow；其他文件类型 fail-closed。
- 只固定排除 `.git/` 与当前 attempt 的 evidence 目录；不读取 `.gitignore`，不接受 request 自定义排除项。
- `changed_files` 是 baseline 与 post-state 的机械差集，按 UTF-8 byte order 排序。每项包含 `change: added|modified|deleted|type_changed`、before/after type、before/after SHA-256 与 byte length；删除项仍保留 preimage SHA-256。
- 任一 changed path 不匹配 `allowed_files` 时，manifest 必须记录 `within_allowed_files: false` 和精确路径，禁止生成 PASS。

### 4. stdout/stderr 与命令身份

每个 command result 必须记录：

- request 中的完整 `executable`、`args`、`cwd` 和 `expected_exit_code`；
- 实际退出码、开始/结束 UTC timestamp 与 duration milliseconds；
- 已解析 executable 的内容 SHA-256（能读取普通文件时）；
- stdout/stderr 各自的 raw byte SHA-256、byte length、是否有效 UTF-8，以及有效 UTF-8 时的 line count。

R1 不落盘原始 stdout/stderr blob，也不截取首尾文本：这能满足独立重跑后逐字节比对，同时不把未经可靠 redaction 的潜在密钥写入仓库。需要保留原文时必须后续单独冻结 redaction/blob 契约，不得在实现中默认开启。

### 5. sealed manifest

`collect` 写入 `instance.json.resources.evidence_store/<task_id>/<attempt_id>/manifest.json`：

- canonical JSON + LF，字段至少包含 request/begin/baseline/post-state SHA-256、平台、命令结果、`changed_files`、越界列表、逐条 acceptance checklist 和整体 `PASS|FAIL`。
- stdout 只输出 `manifest_path` 与 `manifest_sha256` 的单行 canonical JSON；stderr 仅用于稳定诊断。
- attempt 目录已存在封存 manifest、request/baseline 摘要不一致或 begin receipt 不匹配时，必须 fail-closed，不覆盖、不自动递增 attempt ID。
- manifest 本身是可复核证据，不是独立信任证明；控制者必须在 Executor 之外保留 begin stdout 和最终 manifest SHA-256，后续 Reviewer 仍需重跑命令。

### 6. 稳定诊断

诊断继续使用 stdout 空、stderr 单行 canonical JSONL 的既有形式，至少冻结：

- `E_EVIDENCE_REQUEST`：request schema、ID、验收映射或命令字段非法；
- `E_EVIDENCE_PATH`：project、cwd、allowed path、evidence store 或对象类型不安全；
- `E_EVIDENCE_BEGIN_MISMATCH`：request、baseline 或 begin stdout SHA-256 不再匹配；
- `E_EVIDENCE_SEALED`：指定 attempt 已有封存 manifest；
- `E_EVIDENCE_IO`：无法安全读取、同步或发布 evidence 文件；
- `E_EVIDENCE_EXEC`：executable 无法解析或启动。

返回 1 的验收失败不伪装成契约诊断；具体非零退出码、越界路径和未通过 criterion 只写入已封存 manifest。

## 黑盒红灯测试矩阵

批准后的测试必须能编译，并在当前实现上因 `evidence` 命令缺失而失败；不得顺手修改生产实现。

1. 无 Git 项目的 begin/collect：准确得到 added/modified/deleted 及 before/after 内容摘要。
2. 完整 argv 含空格、Unicode 和 shell metacharacter：字面传递，不解析为管道或重定向。
3. stdout/stderr 为空、UTF-8、无效 UTF-8 和无末尾换行：摘要按 raw bytes 确定。
4. 多命令混合 0/非 0 退出：全部事实被封存，整体 FAIL，无手工 `verified` 入口。
5. 每条 acceptance criterion 精确映射 command IDs；空映射、未知 ID 和重复 ID fail-closed。
6. 越界文件、删除文件、类型变化和验证命令新生变更全部进入 `changed_files`。
7. request、baseline、begin receipt 或已封存 manifest 被篡改：零命令执行、零覆盖。
8. 相对路径逃逸、绝对路径、reparse/junction 绕过、特殊文件和路径大小写冲突 fail-closed。
9. `.git/` 和当前 attempt 目录是唯一排除；`.gitignore` 不能隐藏越界产物。
10. Windows amd64、Linux amd64、macOS arm64 运行相同 portable tests；reparse/symlink 平台用例分别报告。

```yaml

  - evidence begin 在任务前封存 request 与无 Git 项目内容基线，collect 必须绑定 begin stdout SHA-256
```

## 实现前检索结论

- `tool/internal/plan` 已有 SHA-256、slash-normalized 相对路径校验、symlink/reparse fail-closed 和 canonical JSON stdout 结构，但这些属于 plan 域，后续实现应提取最小共享工具而非复制逻辑。
- `tool/contracttest` 已有构建 CLI、隔离临时目录、捕获 stdout/stderr 和退出码的 helper，可用于红灯黑盒测试。
- 当前 schema 只安装 install manifest 与 instance manifest；`evidence_store` 只是资源路径声明，没有 evidence request/manifest 或不可覆盖 attempt 实现。
- 当前没有能在 plain directory 任务前后逐字节比较的 baseline，mtime 或最终回复无法替代该能力。

## 明确不做

- 不将本契约扩展为阶段 3 状态机、审计事件链或独立 Reviewer gate。
- 不执行用户提供的 shell string，不支持 pipeline/redirection 语法。
- 不把 Agent 填写的 `verified: true`、mtime 扫描或 Git-only diff 当作通用证据。
- 不将原始 stdout/stderr 默认写入仓库，不在本任务发明不可验证的自动 redaction。
- 不读取或修改 `F:\oioi`，不复用 `e2e-001-a001` 隔离副本，不创建 `a002`。
- 不实现 E 的三次失败自动止损，不运行三平台 CI，不进入阶段 2。
