# 治理工具交付方式选型任务书

## 背景

PoC 已证明仓库本地治理闭环可行，但尚未回答三个产品问题：

1. 如何把治理实例安全、幂等地放入不同技术栈项目；
2. 目标 Agent 在离线或上游不可用时如何继续工作；
3. 上游升级如何更新工具代码而不覆盖项目事实。

Python 只是 PoC 载体。正式选型必须从交付约束倒推，不从已有代码倒推。

## 需求边界

本轮只选择“安装器 + 目标项目本地运行时”的交付方式，并固定升级模型。状态机内部实现细节、云服务和可视化界面不在本轮范围。

## 硬门槛

任一候选命中一条即退出选型：

1. 新 Agent 必须访问方法论源仓库或联网才能执行基本 gate；
2. 升级会无提示覆盖 `AGENTS.md`、`DESIGN.md`、`decisions.md` 或项目本地规则；
3. 无法提供 `plan`/dry-run、幂等 apply 和失败回滚；
4. 无法在 Windows、macOS、Linux 的目标环境建立可重复执行路径；
5. 无法固定 runtime/schema 版本并检测漂移；
6. 身份、人工批准与 CI 信任只能由任务 Agent 自报，且没有降级声明；
7. 许可证不允许目标分发方式。

## 候选方案

### A：纯文件模板复制

安装器只复制 Markdown、JSON 和脚本模板，后续由项目自行维护。

**需要验证的失败条件**：

- 多项目运行时迅速漂移；
- 无法安全升级；
- 模板与项目事实混合后无法三方合并；
- 复制脚本依赖目标环境已有特定解释器。

### B：独立安装器生成并 vendoring 版本化本地运行时

安装器负责 plan/apply/upgrade；目标项目保存带版本和哈希的本地 runtime、schema 与策略，日常 Agent 不依赖全局安装器。

**需要验证的失败条件**：

- vendored runtime 体积或升级冲突不可接受；
- 多平台可执行文件维护成本过高；
- 安全补丁不能及时传播；
- 目标项目误改 runtime 后无法可靠诊断或恢复。

### C：全局 CLI/包，目标项目只保存配置

目标项目运行全局安装的治理 CLI，仓库内只保存 manifest 和项目事实。

**需要验证的失败条件**：

- 新 Agent 环境没有正确版本 CLI；
- 离线或 PATH 差异导致不可运行；
- 不同项目需要不同版本时产生冲突；
- “只读目标仓库即可工作”的核心目标被破坏。

### D：Agent 平台 Skill/插件作为主要运行时

依赖具体 Agent 平台安装 Skill 或插件，目标项目保存少量配置。

**需要验证的失败条件**：

- 锁定单一 Agent 平台；
- Reviewer 与 CI 无法复现插件行为；
- 插件升级不受项目版本控制；
- 平台外 Agent 不能读取和执行治理协议。

该方案可以作为体验增强层，但除非证明可移植和可固定版本，不应默认成为唯一运行时。

## 当前领先假设

**B：独立安装器 + 版本化仓库本地运行时**最符合当前核心目标，但这里只是待证假设，不是决定。它同时保留本地自包含和集中生成/升级能力；代价是 vendoring、跨平台发布和升级协议更复杂。

正式结论必须带来源 URL、PoC 命令、退出码和独立 Reviewer 结果。未满足前禁止创建 `docs/decisions.md`。

## 第一轮官方资料反向调研（未形成决定）

本轮先验证“候选运行时能否成为方案 B 的自包含载体”。以下事实来自官方文档，不把 PoC 所用语言当成默认答案。

| 候选载体 | 官方证据 | 已证实事实 | 对硬门槛的影响 |
|---|---|---|---|
| Python `zipapp` | [Python `zipapp` 文档](https://docs.python.org/3/library/zipapp.html) | 可以分发单个 `.pyz`；目标机器仍必须安装合适版本的 Python；含 C extension 的包不能直接从 zip 运行 | 单独使用 `zipapp` 无法满足“移除安装器 PATH 后，目标仓库仍不依赖全局运行时”的实验 2；除非再捆绑 Python runtime，否则退出正式候选 |
| Node.js SEA | [Node.js Single executable applications](https://nodejs.org/api/single-executable-applications.html) | 目标机不需要安装 Node；支持 `--build-sea`；官方稳定度为 `1.1 - Active development`，并明确 creation process 可能变化；跨平台生成时 snapshot/code cache 必须关闭；Windows/macOS 需要考虑重签名 | 尚未触发硬退出，但要求固定 Node 版本、关闭跨平台不兼容优化并把签名纳入发布流程 |
| Node.js SEA 平台覆盖 | 同上 `Platform support` | 官方 CI 常规测试 Windows、macOS arm64、Linux（排除 Alpine，架构排除 s390x）；macOS x64 当前不受支持且跳过测试 | 若目标平台硬要求 macOS x64 或 Alpine，当前 SEA 直接失败；不能把“Node 通常跨平台”等同于 SEA 已覆盖三平台 |
| Go 原生可执行文件 | [Go command 官方文档](https://pkg.go.dev/cmd/go#hdr-Compile_packages_and_dependencies) | `go build` 将单个 main package 写为平台可执行文件，Windows 自动使用 `.exe`；官方构建约束以 `GOOS`/`GOARCH` 区分目标；包页标注 BSD-3-Clause 与 redistributable | 具备进入自包含、跨平台实验的基础；但本轮尚未证明无 cgo 依赖构建、Ed25519/JCS 库可用性、签名发布和三平台实际运行，不能据此定稿 |

### 本地可实验性快照

2026-11-24 在当前 Windows 开发环境执行运行时探测：

```text
go=NOT_FOUND
node=.../node.exe
v24.19.0
python=.../python.exe
Python 3.13.12
rustc=NOT_FOUND
```

这只说明当前可立即执行 Python/Node 实验，不构成目标用户环境统计。Go 缺失是待补实验环境，不是排除 Go 的依据；在取得受控工具链或 CI runner 前，禁止伪造 Go 实验结果。

### 第一轮结论

1. 架构候选仍以 **B：独立安装器 + 版本化仓库本地运行时**领先。
2. Python `zipapp` 作为唯一运行时已因依赖目标机 Python 而失败；Python 若继续参与，只能验证“同时分发解释器”的成本，不得沿用 PoC 直接转正。
3. Node SEA 保留为正式候选，但 Active development 与平台缺口必须进入风险评分，不能只看“单文件”。
4. Go 是下一轮优先实验候选，不是当前决定。下一步先做最小原生 gate 的 Windows/Linux/macOS 构建与运行矩阵，再比较产物体积、签名、升级和 JCS/Ed25519 一致性。
5. 本轮没有完成交付方式选型，因此 `docs/decisions.md` 仍处于“尚未到创建时机”。

## 评分维度

| 维度 | 权重 | 5 分定义 |
|---|---:|---|
| 目标仓库自包含 | 20% | 无网络、无全局工具也能执行核心 gate |
| 安装与升级安全 | 20% | plan、幂等、三方冲突、回滚全部可验证 |
| 跨平台覆盖 | 15% | 三大桌面/CI 环境有一致入口和测试 |
| 信任边界 | 15% | 身份、批准、CI 结果有外部可信来源 |
| 版本与迁移 | 10% | runtime/schema 可固定并支持跨版本迁移 |
| Agent 可理解性 | 10% | 新 Agent 30 秒内能定位入口和失败原因 |
| 维护成本 | 10% | 发布、补丁和多版本支持成本可承担 |

硬门槛优先于加权分数。任一硬门槛失败，即使总分最高也不能选。

## 必做实验

### 实验 1：两类目标项目安装

- 空白阶段 0 项目；
- 已有 `AGENTS.md`、CI 和未提交改动的阶段 2 项目。

验证：dry-run、首次 apply、第二次幂等 apply、冲突停止、完整回滚。

### 实验 2：本地自包含

安装完成后移除安装器 PATH、断网，在目标项目中启动全新 Agent，运行 inspect、任务校验和失败止损。

### 实验 3：版本升级

目标项目先修改项目事实，再从 runtime/schema v0 升到 v1。验证工具文件更新、项目事实保留、冲突可见。

### 实验 4：信任边界

让任务 Agent 尝试伪造 Reviewer 身份、晋升批准、CI 结果和 trust 文件。记录哪些能被机器阻断，哪些只能明确降级。

### 实验 5：跨平台

在 Windows、Linux、macOS 各运行 plan、apply、doctor、核心 gate；验证路径、编码、权限、换行和 shell 差异。

## 0→1 压力测试

每个候选必须回答：

1. 接入项目从 1 个增长到 100 个时，升级和安全补丁如何传播？
2. Agent 平台从一种增加到三种时，协议是否仍可执行？
3. 核心运行时停止维护时，目标项目如何继续运行和迁移？
4. 两年后最难偿还的兼容债是什么？

## 调研证据要求

每个技术事实必须引用官方文档或项目原始仓库 URL，至少覆盖：

- 运行时支持平台与最低版本；
- 单文件/自包含分发能力；
- 包签名、校验和与发布机制；
- 配置合并或迁移能力；
- 许可证及二次分发条件；
- 对应方案的维护活跃度。

不得凭模型记忆填写许可证、平台支持或安全能力。

## 决策格式

调研完成后，本文件补齐：

```text
决定：选择 [候选]
理由：[硬门槛结果 + 评分 + 实验]
承担的风险：[明确写出]
排除方案：[每项失败条件]
推翻条件：[可观测指标]
Reviewer：[独立运行 ID]
```

然后将正式决定摘要写入 `docs/decisions.md`。在此之前，`docs/decisions.md` 不应存在。
