## Critical findings

### C-1 `DOC_NOT_EXECUTABLE`：manifest 被定义为安装公共输入，但字段契约不完整

- **位置**：`03-治理实例规范v0.md:60-101`
- **风险**：示例包含 `project.name`、`project.git_required`、`integration.ci`，字段语义表却没有定义它们；表中又把实际位于 `governance` 下的 `selection_finalized`、`independent_review_available` 写成未限定路径。`governance.phase` 要求“附判断依据”，但 manifest 没有承载该依据的字段。类型、枚举、未知字段策略、缺省值及版本兼容行为也未定义。两个实现者会生成不兼容的 parser/schema，后续冻结 schema 时需要返工迁移。
- **判定依据**：文档 6 的三问测试要求读者能照文档完成一件事，reference 的每项接口还必须有示例。当前读者无法仅凭本文实现确定性的 manifest 校验器，命中 `DOC_NOT_EXECUTABLE`。
- **修复**：为示例中的每个叶子字段列出完整 JSON path、类型、必填条件、允许值、默认/未知值语义、拒绝错误及示例；增加 `phase_basis`（或明确等价结构）；规定未知字段和 `contract_version` 兼容策略；补一组可复制的有效/无效 manifest 与期望诊断输出。
- **验证**：由两个不共享实现上下文的 Reviewer 分别根据文档写出 JSON Schema，结构应一致；使用同一有效/无效样例集得到相同判定。

## Major findings

### M-1 `maturity.json` 与 `policy.json` 没有唯一权威来源和完整所有权

- **位置**：`03-治理实例规范v0.md:40-58, 103-110, 129-135`
- **风险**：目录说明把 `maturity.json` 称为“可观测成熟度事实”，但所有权表没有说明谁采集、谁批准、哪些字段可由工具更新。`policy.json` 与 `phase.json` 同属共享策略，却没有说明门禁是由 phase 派生还是可独立编辑，也没有冲突时以谁为准。这正是 02 第 62 行已识别的“Agent 可改数字触发升级”风险，03 尚未闭环。
- **修复**：逐文件定义 canonical source、writer、reviewer、更新触发、不可变字段和冲突优先级；把成熟度字段分为机器采集、人工事实和审批结果；明确 `policy.json` 是可重建派生产物或唯一策略源，不能两者兼有。
- **验证**：给出“maturity 与 phase/policy 不一致”的输入样例及 `doctor`/`assess-phase` 唯一预期结果。

### M-2 运行产物的 revision、并发写入、保留和删除生命周期未闭合

- **位置**：`03-治理实例规范v0.md:49-54, 110, 129-135, 151-178, 250`
- **风险**：规范一方面要求运行产物“追加写、关闭后不可改”，另一方面状态机允许 `REVIEW_REJECT → EXECUTING`，但没有定义同一 task 的 evidence/review 如何版本化、哪个 revision 生效、旧 revision 如何引用。`audit/events.jsonl` 又是所有任务共享文件，与“仅自己的 task 命名空间”冲突，且缺少并发追加、原子性、损坏恢复规则。02 第 64 行要求的保留期、压缩、索引、敏感信息清理和归档策略，在 03 中只被推迟为阶段 4 策略；阶段 0–3 仍没有最小生命周期。
- **修复**：定义 artifact ID/revision、不可变文件命名、current pointer 或事件选取规则；规定 reject 后的新 evidence/review 如何关联前序版本；决定审计日志按 task 分片或明确单写者、锁、原子追加和恢复协议；为所有阶段规定最小保留/清理规则，阶段 4 只增强而非首次定义。
- **验证**：提供“首次拒绝后重提”“两个任务并发提交”“归档后重算审计”三个可复制时序样例和期望目录/事件结果。

### M-3 信任材料只描述静态边界，缺少可实现的创建、轮换、撤销和重放状态

- **位置**：`03-治理实例规范v0.md:46, 108, 216-223, 225-237`
- **风险**：规范要求批准绑定 instance ID、阶段、过期时间和 nonce，却没有定义 approval 的规范化签名内容、时间校验、nonce 已使用状态存放位置，以及 `trust.json` 的初始化、轮换、撤销、恢复和升级冲突。只写“人工/CI 初始化、受保护环境修改”不足以形成生命周期；不同实现会产生不同签名和重放语义。
- **修复**：在 `approval.schema.json`/`instance.schema.json` 冻结前明确签名 payload 的规范化规则、实例绑定、时钟/过期容差、nonce 消耗事件、验证算法标识；补 trust anchor 初始化、轮换、双钥匙过渡、撤销和恢复流程，并说明哪些动作必须由外部受信环境执行。
- **验证**：增加跨实例批准、过期批准、已用 nonce、旧锚轮换后批准及撤销锚五组期望失败/成功样例。

### m-2 “目录名可调整”与示例路径之间缺少逻辑资源标识映射

- **位置**：`03-治理实例规范v0.md:36-58, 180-208`
- **风险**：规范声明目录名不是契约，但命令输入输出和完成定义继续直接引用具体文件概念；若正式选型调整目录，调用方可能仍把物理路径当成公共 API。
- **修复**：给关键资源定义稳定逻辑 ID（如 `task_store`、`audit_log`、`trust_anchor`），说明 manifest/instance 如何把逻辑 ID 映射到物理路径。
- **验证**：用两套不同目录布局运行同一逻辑操作序列，得到等价资源引用和审计结果。

## 可操作修复顺序

1. 先修 C-1，冻结 manifest 的完整字段语义与样例；未完成前不要写 schema 或 parser。
2. 再修 M-1，确定每份事实/策略文件的唯一权威源和 writer。
3. 同时修 M-2、M-3，用时序样例冻结 revision、审计并发、保留和信任生命周期。
4. 补 m-1、m-2，并运行两名独立 Reviewer 的“同文档生成 schema/资源映射”一致性测试。
5. 作者修改后重新计算两份文档哈希，发起独立复审；只有 Critical 清零、Major 闭环且三问测试通过，才可建议人工将文档转为 `active`。

## Pre-mortem

如果三个月后接入工具失败，最可能不是 Python 或 Node 选错，而是团队在 manifest 字段、maturity/policy 权威源、批准重放和 evidence revision 上各自做了合理但互不兼容的假设；这些假设一旦进入多个目标项目，就会变成迁移、信任和数据恢复的公共兼容债。当前最便宜的止损点是在实现前把上述语义写成完整字段表与可复制时序样例。
