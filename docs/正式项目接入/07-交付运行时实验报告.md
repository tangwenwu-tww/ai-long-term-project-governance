# T-DELIVERY-003：交付运行时实验报告

## 结论

本轮只得到一个**部分结论**：Node.js 26 SEA 能从 Windows 主机构建 Windows x64、Linux x64、macOS arm64 三种自包含格式；Windows 产物在清空 `PATH` 后直接运行，事件 SHA-256 与 Ed25519 验签均通过。Linux/macOS 只完成交叉生成和文件格式检查，没有在目标系统运行。

本轮不能比较 Go 与 Node：Go 官方分发端点连续三次出现 TLS/连接终止，按项目止损规则停止获取工具链，因此 Go 源码未构建、未运行。此结果是实验环境阻塞，不是排除 Go 的证据。

Node SEA 当前也不能直接定稿：三个最小产物分别约 100 MB、151 MB、145 MB，Windows 产物未签名，且官方文档明确 SEA 仍为 Active development，macOS x64 与 Alpine 不在常规 CI 支持范围。把全平台二进制都 vendoring 到每个目标仓库会造成显著体积和安全补丁传播成本。

首次独立审查的技术复现全部通过，但因 README 不可独立执行和 r001 变更范围无法重算而 REJECT。当前修复依据 [T-DELIVERY-003 r002](./06-交付运行时实验任务单-r002.md) 执行；r001/a001 的范围歧义作为历史保留，不追溯改写为 PASS。

## 工具链来源与完整性

### Node.js

版本固定为 `v26.13.1`，来源为 `https://nodejs.org/dist/v26.13.1/`。下载前从官方 `SHASUMS256.txt` 获取摘要，下载后重新计算：

| 归档 | 官方/实测 SHA-256 | 结果 |
|---|---|---|
| `node-v26.13.1-win-x64.zip` | `e2edda75bfb089654705cf65a13b58933bfd5f57148e8ebda916f58a2474f1f7` | PASS |
| `node-v26.13.1-linux-x64.tar.gz` | `518674de2b621728a5e4486f5fb3b7d2900bb3cc4aa97969edaa463db99f9778` | PASS |
| `node-v26.13.1-darwin-arm64.tar.gz` | `aec2514ea1ceb2ba52455e9ec65986f6749a06dd759e5db2a72e6889668c9735` | PASS |

当前系统自带的 Node 是 `v24.19.0`，`node --help` 只有旧的 `--experimental-sea-config`，没有当前文档的 `--build-sea`。因此实验显式使用校验后的 Node 26 便携工具链，不能隐式依赖机器 PATH。

### Go

`winget show --id GoLang.Go --exact` 返回 Go `1.27.4`、BSD-3-Clause、官方 MSI URL 和 SHA-256；但实际获取工具链失败：

1. `Invoke-RestMethod https://go.dev/dl/?mode=json`：传输 EOF；
2. `curl` 读取同一官方清单：TLS handshake 失败；
3. `winget download --id GoLang.Go --exact`：连接意外终止，退出码 `0x80072efe`。

三次属于同一个“go.dev 分发连接终止”failure signature，随后停止。没有使用非官方镜像，也没有安装系统级 Go。

这三次 stdout/stderr 没有在发生时写入独立 evidence 文件，只有当前报告与会话工具输出摘要；网络失败又不可稳定重放，因此“恰好三次且属于同一 signature”**不能由后续 Reviewer 独立证明**。本报告只据此解释作者为何停止，不把它当作排除 Go 或评估 Go 能力的证据。下一次外部环境恢复后，必须从第一次尝试开始封存 UTC 时间、命令、退出码、规范化 stdout/stderr 与 SHA-256。

## 实验输入

`experiments/delivery-runtime/` 仅包含最小、一次性实验源码：

- Go/Node 都对事件向量 1 的既定 canonical bytes 计算 SHA-256；
- 都验证 `TRUST_INIT` owner 的既定 Ed25519 签名；
- Node SEA 关闭 snapshot/code cache，符合官方跨平台生成限制；
- `execArgvExtension` 设为 `none`，避免目标环境通过 `NODE_OPTIONS` 扩展运行参数。

构建输出、下载归档和工具链位于 `.gitignore` 覆盖的 `out/`、`downloads/`、`toolchains/`，不属于 canonical source。

## Node SEA 结果

### Windows 实际运行

先用 Node 26 直接运行 `main.js`，再执行：

```powershell
node.exe --build-sea .\sea-config.json
```

构建退出码为 `0`。随后临时将子进程 `PATH` 清空，直接运行 `governance-node-sea.exe`，退出码为 `0`，输出：

```json
{"runtime":"v26.13.1","platform":"win32","arch":"x64","event_sha256":"81588443ac9948f2eda8f0269294b006d10be5d8f4e7dcf4bb23ef17a88d624d","hash_matches":true,"owner_signature_ok":true}
```

这证明该 Windows 产物执行时不需要 PATH 中存在 `node`，但不证明它在所有 Windows 版本、权限策略或安全软件环境中可运行。

### 交叉生成结果

| 目标 | 构建退出码 | 实际执行 | 字节数 | 文件魔数 | 产物 SHA-256 |
|---|---:|---|---:|---|---|
| Windows x64 | 0 | PASS（当前主机、空 PATH） | 100,233,032 | PE | `952c61ec37878536d3a96c5a65433cd31769b8b8bdac523e1d18c4f0e4cd42ff` |
| Linux x64 | 0 | **未验证** | 150,699,136 | `7F454C46`（ELF） | `04c21b14e7678228670a3bc438a17e733a58b0400d9d73fea0df65ed372caaf0` |
| macOS arm64 | 0 | **未验证** | 145,415,332 | `CFFAEDFE`（Mach-O） | `78b870f89367319256479cbf42c722ace89c2b834cd6e33549b53b957a04b5e7` |

同一工具链、源码和配置连续构建两次，三种产物的前后 SHA-256 均完全一致。该结果证明当前主机上的重复构建确定性，不等同于不同 CI 主机的 reproducible build。

`Get-AuthenticodeSignature` 对 Windows 产物返回 `NotSigned`。官方 Node 文档要求 macOS 产物签名，并建议 Windows 使用证书签名；正式发布实验必须覆盖签名后哈希清单、验证链和重签顺序。

## 失败与恢复记录

| failure signature | 次数 | 证据质量 | 处理 |
|---|---:|---|---|
| go.dev 分发 TLS/连接终止 | 3 | 仅作者会话摘要，缺原始 evidence，后续不可独立证明 | 按规则停止 Go 获取；不用于排除或评分 Go |
| Windows `tar` 缺少 xz filter | 1 | 会话输出 | 使用官方同时发布且哈希已验证的 `.tar.gz` |
| 全量解包在中文路径创建 npm/npx symlink 失败 | 1 | 会话输出 | 只在随机临时目录精确提取 `bin/node`，不依赖 npm/npx |
| 初次 SEA 命令解析了错误的相对根路径 | 1 | 会话输出 | 修正为从实验目录解析父目录；未发生构建副作用 |
| PowerShell `foreach` 直接接 pipe 的语法错误 | 2 | 会话输出 | 改为先收集 `$rows` 再格式化；未达到三次停止线 |

## 对选型的影响

1. Node SEA 通过了 Windows 自包含的最小门槛，并证明可以从单一主机交叉生成三种目标格式。
2. Node SEA **尚未通过**三平台运行门槛；Linux/macOS 的结果只能叫“可生成”，不能叫“可交付”。
3. 最小二进制已经达到 100–151 MB。若每个项目 vendoring 当前平台单个 runtime，仍需评估仓库膨胀；若 vendoring 全平台集合，成本明显不可接受。
4. Node SEA 的运行时版本、安全补丁和代码签名会成为项目本地升级责任；这强化了“runtime 清单 + 哈希 + upgrade plan”的必要性，也提高了方案 B 的维护成本。
5. Go 仍是优先候选，因为理论上更适合小型原生 CLI，但在本轮没有任何构建证据。后续不得以预期体积或静态链接能力替代实测。
