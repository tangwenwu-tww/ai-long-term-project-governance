# 正式项目如何接入 AI Agent 治理方法论

## 用途

当一个真实项目准备长期使用 AI Agent 开发时，按本文把本仓库的通用方法论转成目标项目自己的治理文件、任务协议和机器门禁。

本仓库是方法论源，不是业务项目。业务 Agent 应以目标项目仓库里的本地规则为准，不应在每次任务中跨仓库通读全部方法论文档。

`draft` 文档是待审材料，不得作为实现依据。完成独立 Review 与人工定稿后，逐份转为 `active`；在此之前禁止根据其中的候选结构直接开发安装器。

## 不适用

- 一次性脚本、短期实验或纯问答任务，不需要完整接入。
- 尚未明确产品核心假设时，只做阶段 0 的需求边界与反向调研，不创建空的 `decisions.md`。
- 本文不代替各阶段手册；确定阶段后仍需读取对应的 active 手册。

## 接入后的三层形态

```text
本方法论仓库（上游规范与模板）
        ↓ 按阶段实例化
目标项目治理层（项目事实、规则、任务与证据）
        ↓ 每次会话强制读取和执行
AI Agent 运行层（计划、实现、审查、止损）
```

目标项目中的规则必须是项目专属事实，例如当前阶段、技术栈、核心假设、已定决策、允许修改范围和既有设计基线。不要把仍带占位符的通用模板直接当成正式规则。

## 怎么用

### 1. 先判断目标项目处于哪个阶段

主 Agent 根据可观测事实判断阶段，不按项目运行时间判断：

| 阶段 | Agent 层面的主要形态 |
|---|---|
| 0 | 主 Agent 调研、拆解候选方案；人工定稿方向与骨架 |
| 1 | 单 Executor Agent + 自动检查与可复核证据，只验证核心流程 |
| 2 | Executor Agent + 独立 Reviewer Agent |
| 3 | Orchestrator、Planner、Executor、Reviewer + 状态机与证据门控 |
| 4 | 增加独立根因分析、安全模式、自动止损与长期审计 |

未满足升级条件时，不得为了“看起来规范”提前启用后续阶段的重型治理。

### 2. 在目标项目建立本地治理入口

初始项目不需要预先整理成以下格式。接入工具应先识别并保护项目原有事实，再按当前阶段渐进创建实际需要的最小文件集；Git、frontmatter 和 `docs/tasks/` 都不是首次接入的统一前置条件：

```text
目标项目/
├─ AGENTS.md
├─ DESIGN.md                 # 仅当前端项目已有明确设计事实时创建
├─ docs/
│  ├─ decisions.md           # 仅完成选型定稿后创建
│  ├─ tasks/                 # 结构化任务单
│  ├─ adr/                   # 有长期决策时逐项创建
│  └─ runbooks/              # 达到相应阶段且确有运行场景时创建
├─ evidence/                 # 阶段 3 需要结构化证据时创建
└─ scripts/                  # 将高频规则转成机器检查时创建
```

`AGENTS.md` 是每次 Agent 会话的唯一启动入口。它至少写明：

- 当前阶段；
- 技术栈；
- 核心假设；
- 强制阅读顺序；
- 当前项目的禁止事项；
- failure signature 与升级规则。

发现预期文件不存在时，Agent 必须先判断它是“尚未到创建时机”“当前阶段必须存在”还是“已经废弃”，不得直接报告缺失或自行创建占位文件。

### 3. 固定每次 Agent 会话的启动协议

每个 Agent 按以下顺序启动：

1. 完整读取目标项目的 `AGENTS.md`；
2. 若 `docs/decisions.md` 已存在则读取；
3. 确认当前阶段，只启用该阶段允许的动作；
4. 读取与当前任务相关且 `status: active` 的文档；
5. 前端任务额外读取 `DESIGN.md`；
6. 检查任务是否包含验收标准、允许修改范围和实现前检索；
7. 条件不满足时停止实现，先补齐任务契约。

### 4. 用任务契约约束单次实现

最小可复制示例：

```yaml
task_id: T-001
title: "为空输入增加明确的 400 响应"
phase: 1
acceptance_criteria:
  - "空输入返回 HTTP 400"
  - "合法输入仍返回 HTTP 200"
allowed_files:
  - src/api/submit.ts
  - tests/api/submit.test.ts
pre_implementation_search:
  commands:
    - "rg -n 'validateInput|空输入|400' src tests"
  evidence_required: "列出匹配实现，并说明复用或新增的理由"
doc_type: none
doc_purpose: ""
```

Executor Agent 的固定执行顺序：

```text
读取项目约束
→ 检索已有实现
→ 确认 allowed_files
→ 实现与相关测试
→ 记录命令、退出码和 changed_files
→ 交给独立 Reviewer（达到阶段 2 后）
→ 将长期有效的新事实沉淀回项目文件
```

### 5. 随阶段把软规则升级为机器门禁

不要长期依赖 Agent 自觉记住规则。某类错误重复出现后，依次把规则落到：

1. 项目 `AGENTS.md`；
2. 任务单必填字段或审查清单；
3. lint、静态检查、测试路由或 CI gate；
4. 状态跃迁和自动止损程序。

适合机器化的项目包括：修改范围校验、重复实现检测、测试选择、证据包格式、退出码、failure signature 计数和文档状态检查。业务语义与视觉一致性仍需要独立 Reviewer 判断。

### 6. 保持上游方法论与项目实例分离

- 本仓库负责维护通用规则、阶段手册和模板。
- 目标项目负责维护自己的事实、决策、踩坑规则和证据。
- 上游规则更新时先比较差异，再由目标项目决定是否采纳；不得直接覆盖目标项目的 `AGENTS.md`、`decisions.md` 或 `DESIGN.md`。
- 目标项目出现可复用的高频问题时，再提炼为本仓库的通用规则，避免把单个项目的偶发现象扩散到所有项目。

## 接入验收

完成接入后，应能逐条回答：

- 新 Agent 是否只读取目标仓库就能知道当前阶段和允许动作？
- 未完成选型时，Agent 是否不会创建 `decisions.md`？
- 每项实现是否有验收标准、`allowed_files` 和实现前检索？
- Agent 是否能提供命令、退出码和实际变更文件？
- 达到阶段 2 后，作者与 Reviewer 是否是独立上下文？
- 同一 failure signature 连续三次时，流程是否会停止并升级？
- 上游模板更新是否不会覆盖目标项目已经确认的事实？

任一答案为“否”，说明接入尚未形成闭环。

## 常见错误 / 注意事项

- 不要把全部方法论文档设为每次会话必读；只读当前任务相关内容，避免上下文被治理文档占满。
- 不要在项目刚开始时直接启用阶段 3 的四角色和证据状态机。
- 不要用空 `decisions.md`、空 `DESIGN.md` 或占位 ADR 假装治理产物已经存在。
- 不要让 Executor Agent 自己完成最终审查；阶段 2 起必须使用独立 Reviewer。
- 不要只把规则留在聊天记录中；长期有效的事实必须进入目标仓库。
- 不要让上游同步脚本无条件覆盖项目本地规则。
