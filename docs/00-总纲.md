# 文档 0：总纲——AI 长期开发复杂项目的实现体系

## 一句话体系

**约束密度随项目成熟度递增，每个阶段只上该阶段负担得起的治理，用可观测信号触发升级，而不是按日历推进。**

## 五阶段时间线

| 阶段 | 名称 | 核心任务 | 约束密度 | 进入条件 |
|---|---|---|---|---|
| 0 | 地基 | 调研、选型、最小约束（3–5 天） | 极轻 | 有产品想法 |
| 1 | MVP 验证 | 跑通核心假设，不建治理 | 轻 | 阶段 0 完成 |
| 2 | 过渡加固 | 关键路径测试、两角色、发版校验 | 中 | 核心假设为真 |
| 3 | 持续迭代 | 状态机、证据门控、测试分层、文档治理 | 重 | 阶段 2 验收通过 |
| 4 | 长期运营 | 疑难止损、安全模式、规则复核与降档 | 重 + 动态 | 存在长期 SLA/合规责任 |

## 当前状态

项目仍处阶段 1。`e2e-001-a001` 的历史结论保持 `CORE_HYPOTHESIS_NOT_PROVEN`：A/C/F PASS，B 为 `LOCAL_ENTRY_FACT_GAP`，D 为 `NOT_VERIFIABLE`，E 为 `CAPABILITY_MISSING`。`T-ENTRY-001/002` 已完成并提交入口修复能力，但尚未运行新的 E2E attempt，因此 B 只能记为“修复已实现、待复验”，不能改判 PASS；D/E 仍是独立阻塞项。

当前 `T-EVIDENCE-001/002` 已完成契约、红灯基线与生产实现：`evidence begin/collect` 已能机器封存无 Git 内容基线、完整 argv/退出码、stdout/stderr 摘要、内容变更清单与验收映射。这表示 D 的修复能力已实现，但尚未运行新 E2E attempt，不能把 a001 改判为 PASS。下一任务是 `T-HALT-001` 自动止损契约；之后运行三平台 CI，最后以新隔离 attempt 重跑 A–F，在此之前不进入阶段 2。

## 常驻规则（五阶段全程生效）

1. **重试上限**：一次尝试 = 从代码/配置/测试预期/依赖变更开始，到验证命令执行完毕产生新退出码为止。同一 failure signature 连续 3 次失败 → 人工介入；成功一次即清零。
2. **踩坑即规则**：同一个错误被纠正第二次，立即写入 `AGENTS.md`。完整的三级止损跑表见 [文档 9：AI 重复踩坑怎么处理](./09-犯错处理.md)。
3. **证据优先于自述**：任何“完成了”的声称，必须附带命令和退出码。0→1 简化为“贴出命令和输出”，1→99 升级为结构化证据包。
4. **审核随阶段升级**：阶段 1 不设人工/独立 Reviewer 合并门禁，以自动检查和可复核证据为准；作者机械自检不得冒充独立审查。作者不审自己从阶段 2 起生效，之后不放松。

## 升级 / 降档触发信号

| 信号 | 动作 |
|---|---|
| 核心假设被证明可跑通 | 阶段 0 → 1 |
| 第一个真实外部用户 / 代码约 2 万行 / 首次线上故障 | 阶段 1 → 2 |
| 团队 > 1 人 / 并行 Agent 会话 > 3 / 模块被 3 个功能复用 / 出现合规需求 | 阶段 2 → 3 |
| 出现需长期承担 SLA 的模块 | 阶段 3 → 4 |
| 产品线砍掉 / 进入维护冻结 | 主动降档，关掉不再产生收益的闸门 |

**AI 行为病症信号**（在项目跨过 0→1 后重点观察，任一出现即意味着该上对应治理，比用户数/行数这类宏观信号更早）：

| 信号 | 含义 | 动作 |
|---|---|---|
| AI 在已实现功能的文件里写出风格不一致的实现 | 规范执行松了 | 收紧规范并加强审查（文档 7） |
| 同一功能被 AI 用不同方式实现 2 次以上 | 该沉淀组件/工具函数了 | 抽公共层建复用；引入 `DUPLICATE_LOGIC` 阻断（文档 7） |
| 新功能开发时间变长（非因复杂，而要理解已有代码） | 需要重构和文档更新 | 运行文档巡检（文档 13）+ 技术债还债排期（文档 4 §5） |
| 出现「不敢改」的代码区域 | 缺测试 / 设计过耦合 | 补测试、简化设计（文档 12） |

## 核心原则

- **0→1 约束“做什么”，1→99 约束“怎么改”**。
- **每一次踩坑或纠正，都应转化为仓库中的一个文件、一条规则或一个脚本**，而不是留在聊天记录里。
- **看不懂的文档比没有文档更有害**，因为 AI 会把它当事实采纳。
