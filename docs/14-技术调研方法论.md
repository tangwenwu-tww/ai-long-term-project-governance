# 文档 14：技术调研方法论（先调研拆解，再写可执行方案）

## 用途

当要「做一个含技术选型的新功能」「评估能否二开某个开源项目」「决定自研还是复用存量开源」时，默认让 AI 走完下面这套**强制调研闸门**，再允许写第一行业务代码。它把「让 AI 先调研、再给可执行方案」从一句叮嘱变成可执行的步骤，并且把结果**固化成仓库里的决策文档**，防止 AI 后续会话推翻自己。

**核心问题：直接让 AI 动手会怎样？**

AI 能力强，但「直接开始」意味着它会在无约束下自由发挥：选型可能凭印象（尤其许可证/授权这类凭记忆极易出错）、可能没读懂就改、可能新一轮会话又从别的方案重新开始。技术调研方法论要解决的就是这三件事：**强制带来源、强制先拆解、强制沉淀决策**。

## 一条总原则

> **技术创新度越低，越应该复用存量开源，而不是自研。**

理由不是「AI 不如人」，而是：

1. **存量开源项目在复杂难定位的 bug 上更稳定**。这类 bug 通常已被人踩过、提 issue、修过，你白捡的是别人多年撞坑的成果。
2. **很多「不符合直觉的写法」不是写得丑，是在兜一个你没遇到过的边界 bug**。删掉它「重构清爽」的那刻，可能正好把那个 bug 找回来。自研 = 自己重新撞一遍所有坑；二开 = 白捡别人多年撞坑的成果。
3. **降低心智负担是硬收益**：读存量代码只需理解「它为什么这样」（填空题）；自研要发明「该怎样」（创作题）。前者成本低得多。

## 两个默认与三条破例

**默认动作**：发现成熟开源 → 二开 / 复用，不重复造轮子。

**自研仅在下三者之一成立时启动，且必须书面举证理由**：

| 触发条件 | 说明 | 优先级 |
|---|---|---|
| 许可证 / 合规冲突 | 如 GPL 传染 vs 闭源分发 | **最高，先查许可证** |
| 需深度改内核且上游拒绝收敛你的 PR | fork 后每升一版都要重合并上游 diff，分叉成本极高 | 中 |
| 项目已僵尸化 | 「存量」≠「成熟」：无维护、无文档、bug 长年不修的不算成熟开源 | 低 |

## 五个执行步骤

### 第 1 步：定需求边界（先于一切）

先写清「我们只做 A、B、C」，哪怕一句话。没有边界，调研必然开花一片。

示例（正向表达，不写「不做 X、没用 Y」）：

> 我们不做录屏内核，只做界面汉化 + 增加云存档 + 接入导出。

### 第 2 步：反向验证调研

**不是问 AI「哪个方案最好」，而是问「每个候选在什么条件下必然失败、硬门槛是什么」。** 这一步应列 2–4 个候选方案（如：直接二开、fork 仅打包、借鉴其技术栈自研、前端壳 + 复用录制后端），逐个论证。

**硬性要求（写给 AI 的调研指令要点）：**

- 所有结论**必须带来源 URL**，禁止凭记忆断言，尤其许可证 / 授权这类极易出错的。
- 每个候选必须写清：技术栈、核心 README/文档、核心模块（如录屏后端是原生采集还是 ffmpeg/WebRTC）、硬门槛（跨平台？静默录制？CPU 占用？能否拿到原始帧二次加工？许可证允许闭源二发吗？）。
- 结尾输出一页纸：候选矩阵 + 硬门槛 + 推荐结论。

**0–1 选型另加「压力测试四问」**：泛模板（直接二开 / 自研 / 换栈复用）只问失败条件是不够的，0–1 的选型枷锁在于「换一次代价极高」，所以要逼 AI 对每个候选**模拟未来**，而非只列当下的对比表：

> 请针对候选方案 A 和 B，分别模拟以下场景：
> 1. 用户量从 0 增长到 100 万，架构需要几次重构？
> 2. 团队从 1 人扩展到 5 人，协作成本如何变化？
> 3. 如果核心依赖突然停止维护，迁移路径是什么？
> 4. 两年后回头看，哪些技术债是必然会出现的？
> 给出明确推荐，并说明你愿意为这个推荐承担什么风险。

这四问主要服务「是否有长期路径」，对应硬门槛里的「可行生产路径」；进入 1–99 后不再需要这么重的选型调研，只评估新功能对现有架构的冲击即可。

### 第 3 步：选型定稿并记录

把「为什么选 / 为什么排除 / 什么条件下推翻」写进决策文档。**作用不是给人看，是防止 AI 下一轮会话自己推翻自己。** 格式可参考 ADR 模板（`docs/08-模板库.md` §8.3）：背景 / 选项 / 决定 / 推翻条件。

### 第 4 步：读懂架构再动手

选型过关后，进入代码拆解，产出**「改动地图」**，而不要直接开始改：

- 目录结构，UI 层 / 录制层 / 导出层的分界在哪；
- 核心入口与核心函数（如 `startRecording`、`encodeFrame`）；
- 关键依赖（ffmpeg 绑定、GPU 编码、跨平台原生采集）；
- 需要改动的最小文件集。

**判断「必须新增/修改」时，须先检索现有组件并附结果**，说明为何不可直接复用。没有这张地图，后续改动都是盲改。

### 第 5 步：沉淀而非交差

过程中每次踩坑、每次纠正，转成一个文件 / 一条规则，而不是留在聊天记录里。这样下一轮新会话从文件出发，不重新踩。所有「完成了」的声称须附命令与退出码。

## 不适用

- 改动极小且无选型（改错别字、查一个事实、跑一条命令、纯格式转换）→ 不需要本方法论，会拖慢节奏。
- 项目已有明确技术栈且本次改动不触及选型 → 只走第 4、5 步的「拆解 + 沉淀」，跳过前三步。
